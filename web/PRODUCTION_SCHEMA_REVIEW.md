# Production dashboard schema review

`supabase/production_dashboard.sql` is a proposed single transaction derived from `schema.sql`, 002 and 004. It is **not applied**. It requires existing Supabase `auth.users`, `auth.uid()`, `auth.jwt()`, `anon` and `authenticated` roles, and access to `gen_random_uuid()`. Execute as a role permitted to create and administer these public tables and policies. Confirm the exact production project and these prerequisites first; no production credentials are in this repository.

The transaction checks for the three target relations and their identity sequence and stops if any exist. It does not attempt to upgrade, drop, or alter pre-existing data. On any error, ensure the transaction has rolled back (`ROLLBACK` if the editor leaves the session in an aborted transaction). Do not rerun it on any nonempty installation; inspect its existing schema and migration history and prepare a separate reviewed upgrade. Manual SQL editor execution does not automatically prove that migration tooling has recorded the migration.

Corrections: RLS and own-user SELECT/INSERT/DELETE, bounded fields and unique (user_id, request_id). OAuth client-bearing JWTs are blocked from direct table access. Clients: authenticated browser SELECT only. Grants: authenticated browser SELECT/DELETE only for its own rows, with explicit restrictive INSERT/UPDATE denial. All three tables explicitly revoke PUBLIC/anon/authenticated privileges before granting only these privileges, and the sequence receives authenticated USAGE/SELECT. No transient browser grant-creation policy exists at any point. Trusted database owners or privileged service roles remain powerful; this SQL does not remove their privileges or revoke privileges from other pre-existing roles. Check the target project's Data API exposure and role privileges; explicit grants are required when automatic exposure is disabled. No MCP clients or grants are seeded. Draft 003, consent page and MCP endpoint remain disabled. User account deletion cascades into corrections and grants.

After execution, run `supabase/production_verify.sql`; check all output, including all ACLs, role memberships, RLS, policies and column privileges. Run a separately reviewed rollback-only two-user synthetic RLS/forgery/revocation test before accepting real data. Check Google browser JWT claim behavior and direct OAuth Data API denial against this exact configuration. Real PostgREST and hosted tests have not been performed for this consolidated file. No guarantees are made about other roles, functions, default privileges or environment settings until inspected.

Minimal action-time approval: apply this exact transaction once in the explicitly identified new production Supabase project after confirming the destination, no matching existing objects, and a suitable recovery plan. It creates three persistent tables, RLS policies and the stated role access; it does not publish the app or activate MCP. A separate approval is needed to perform a rollback-only hosted synthetic test and for any later policy, OAuth, deployment, billing, or user-data change.
